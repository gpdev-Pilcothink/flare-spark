# DGX Spark에서 FLARE 실행하기

[English](README.md) | **한국어**

모델 준비와 네이티브 서빙에 사용할 Docker 이미지 하나를 직접 빌드하거나 Pull한 뒤, 헤드 노드에서 명령 한 번으로 여러 DGX Spark를 실행하는 프로젝트입니다.

[NVIDIA FLARE](https://github.com/NVIDIA/flare-local-inference)를 사용합니다. Ignition이 PyTorch와 FlashInfer/B12X로 모델을 준비하면, Rust로 작성된 Flare 서버가 완성된 패키지를 불러옵니다. 별도의 `flare_cluster.sh`가 Docker와 SSH를 통해 각 노드의 실행을 관리합니다.

## 필수: 공식 클러스터 설정과 NCCL 테스트

> [!IMPORTANT]
> **이 저장소의 다중 노드 가이드를 실행하기 전에 NVIDIA 공식 DGX Spark 플레이북에 따라 네트워크 설정을 완료하고, NCCL 통신 테스트까지 통과해야 합니다.** ping이나 SSH 접속 성공만으로 GPU 집단 통신이 검증된 것은 아닙니다.

사용할 노드 수와 네트워크 연결 방식에 맞춰 아래 공식 플레이북을 순서대로 진행하세요.

1. [여러 DGX Spark 연결하기](https://build.nvidia.com/spark/connect-multiple-sparks) — 케이블 연결, 네트워크 인터페이스와 비밀번호 없는 SSH를 설정합니다. NVIDIA Sync Cluster Assistant로 이미 클러스터 설정을 성공적으로 완료했다면 수동 네트워크 설정을 반복하지 마세요.
2. [NCCL 설정과 통신 검증](https://build.nvidia.com/spark/nccl/stacked-sparks) — 실제 사용할 모든 노드를 대상으로 안내된 NCCL 테스트를 빌드하고 실행합니다. 구성에 따라 [2대 직접 연결 테스트](https://build.nvidia.com/spark/nccl/two-nodes) 또는 [4대 스위치 연결 테스트](https://build.nvidia.com/spark/nccl/four-nodes)를 선택하세요.

통신 오류가 있다면 모델 준비를 시작하기 전에 해결하세요. 테스트를 통과한 뒤 이 문서로 돌아와 이미지 준비와 모델 가이드를 진행하세요. 이후 실행 스크립트의 RoCE 사전 검사도 별도로 수행됩니다.

## 준비 사항

- NVIDIA 드라이버와 NVIDIA Container Toolkit을 통한 GPU Docker 실행이 정상 동작하는 Linux DGX Spark. 선택한 노드 수는 사용할 모델 레시피가 지원해야 합니다.
- 선택한 모든 노드 간의 RoCEv2 IPv4 통신과 `/dev/infiniband` 접근.
- 헤드에서 모든 워커로 비밀번호 입력 없이 접속할 수 있는 SSH 키 설정.
- 모든 노드에서 Docker를 실행할 수 있는 권한.
- 헤드에 설치된 `bash`, `docker`, `ssh`, `python3`, `curl`, `ss`, `flock`, `realpath`, `sha256sum`. 가이드에서는 헤드의 노드 간 통신 주소를 얻기 위해 `ip`도 사용합니다.
- 모든 노드에서 **동일한 절대 경로**를 사용하는 쓰기 가능한 상태 디렉터리. 각 노드의 로컬 SSD를 사용해야 합니다.
- 헤드에 준비된 원본 체크포인트 또는 Ignition이 내려받을 수 있는 공식 모델 별칭.

각 워커는 공식 준비 프로토콜로 필요한 체크포인트 범위를 전달받습니다. 워커마다 전체 원본 체크포인트를 따로 복사할 필요는 없습니다. 모델 준비 전에는 다른 GPU 추론 작업을 종료하세요.

## 1. 헤드에서 필요한 파일 내려받기

이미지를 Pull해서 사용하더라도 헤드에 [flare_cluster.sh](flare_cluster.sh)는 반드시 내려받으세요. GitHub에서 각 파일을 열고 **Download raw file**을 사용하거나, 저장소 ZIP을 내려받은 뒤 이 README가 있는 디렉터리를 여세요.

다음 단계로 넘어가기 전에 파일이 있는지 확인하세요.

```bash
ls -l flare_cluster.sh
```

워커에는 스크립트를 복사하지 않아도 됩니다. 헤드가 SSH로 워커를 제어합니다. `bash flare_cluster.sh`로 실행하므로 실행 권한을 별도로 바꿀 필요도 없습니다.

## 2. 헤드에서 이미지 Pull하기

```bash
docker pull pilcothink/flare_spark
```

호스트의 `flare_cluster.sh`가 필요합니다. `--sync-image`로 이미지를 워커에 전달할 수 있습니다.

| 구성 요소 | 빌드 기준 |
|---|---|
| FLARE 소스 | `d5fd9824593c2a70f6bdc001b39f16b4c5b3b0b4` |
| 기반 이미지 | `nvidia/cuda:13.2.0-devel-ubuntu24.04` |
| Python | 3.12 |
| PyTorch | 원본 잠금 파일의 `2.14.1+cu132` |
| Rust | 1.94.1 |
| 모델 준비용 종속성 | 고정한 원본 `uv.lock` |
| 네이티브 빌드 종속성 | 고정한 원본 Cargo 잠금 파일 |

이미지 하나에 Ignition과 네이티브 Flare 실행 파일이 모두 들어갑니다. 준비용 이미지를 별도로 빌드하거나 배포하지 않습니다. UV와 Cargo는 BuildKit의 영구 빌드 캐시를 사용합니다.

Dockerfile은 고정된 cuSPARSELt 0.8.1 ARM64 wheel의 패키징 문제를 보정합니다. 실제 라이브러리는 AArch64이지만 내부 플랫폼 태그가 `sbsa`로 되어 있어, 아키텍처를 확인한 뒤 해당 메타데이터와 기록을 수정합니다. 라이브러리 바이너리와 버전은 바꾸지 않으며, 종속성 검사도 유지합니다. 모델 계산 소스에는 패치를 적용하지 않습니다.

## 3. 실행 시 이미지 전달 방식 선택하기

헤드에서 이미지를 Pull한 뒤, 아래 전달 방법 중 하나를 선택하세요. 이미지 준비와 전달은 별도 단계입니다. **`--sync-image`는 `docker build`나 `docker pull`이 아니라 실행 스크립트의 인자입니다.**

**자동 전달:** 가이드의 실행 명령처럼 `--workers` 다음에 `--sync-image`를 넣으세요. 명령을 실행하면 다음 순서로 진행됩니다.

1. 헤드의 로컬 이미지를 확인하고, 지정한 각 워커에 SSH로 접속합니다.
2. 각 워커의 이미지 ID와 헤드의 이미지 ID를 비교합니다.
3. 이미지가 없거나 다르면 헤드의 `docker save` 출력을 SSH로 보내 워커의 `docker load`로 불러옵니다.
4. 이미지 ID가 같아졌는지 다시 확인한 뒤 모델 준비 또는 패키지 재사용으로 넘어갑니다.

이미지가 이미 같으면 전달을 건너뜁니다. 목록에 있는 모든 워커를 검사합니다. 이 옵션은 이미지를 빌드하거나 체크포인트를 내려받거나 호스트의 실행 스크립트를 복사하지 않습니다. 준비된 모델 패키지는 이후 FLARE가 별도로 전달합니다.

**수동 전달:** 헤드에서 이미지를 파일로 저장하고 직접 복사한 뒤, 모든 워커에서 불러오세요.

```bash
# 헤드
docker save -o flare_spark.tar pilcothink/flare_spark

# 파일을 복사한 뒤 각 워커에서 실행
docker load -i flare_spark.tar
```

`--sync-image` 없이 실행하면 이미지 ID가 다른 워커가 있을 때 중단합니다. 이미지를 자동으로 pull하거나 워커를 자동 탐색하지 않습니다. SSH 접속 대상은 `--workers`로 직접 지정합니다.

## 4. 모델 가이드를 선택하고 헤드에서 실행하기

[Guide/](Guide/)에서 사용할 가이드를 선택하고 해당 문서의 전체 실행 명령을 사용하세요. 모델 선택, 지원하는 rank 수, 컨텍스트 용량, 동시 요청 수, MTP 설정과 실측 결과는 각 모델 가이드에서 다룹니다.

`flare_cluster.sh`는 헤드에서만 실행하며, SSH로 워커 컨테이너를 시작하고 종료합니다. `--workers`에는 헤드를 제외한 워커만 쉼표로 구분해 넣고 사이에 공백을 넣지 마세요. 전체 rank 수는 헤드 1대와 지정한 워커 수를 합해 계산하며, 사용할 모델 레시피가 그 수를 지원해야 합니다.

실행 순서는 다음과 같습니다.

1. SSH와 이미지 ID를 확인합니다. `--sync-image`가 있을 때만 이미지가 없거나 다른 워커에 이미지를 전달합니다.
2. 모든 선택 노드에서 I/O 권한, 내보내기·캐시 경로의 쓰기 권한, 로컬 서명 주체와 RoCE 통신 연결을 확인합니다.
3. 일치하는 완성 패키지가 있으면 재사용합니다. 없으면 헤드에서 공식 `ignition export`, 각 워커에서 `ignition join`을 실행합니다. 새 모델 준비 과정은 가중치 로딩, 커널 튜닝·컴파일, 모델 순전파 컴파일, 그래프 캡처와 서명된 패키지 내보내기를 포함합니다.
4. 공식 `flare inspect`로 패키지를 검증하고 모든 rank에서 공식 `flare run`을 시작합니다. FLARE가 각 워커의 패키지를 전달하고 검증한 뒤 GPU에 불러옵니다.
5. 가중치와 실행 자원을 불러오고, 캐시를 할당하고, 서빙용 통신을 연결한 뒤 헤드의 HTTP 서버가 준비될 때까지 기다립니다.

**최초 모델 준비에는 1시간 이상 걸릴 수 있습니다.** Docker 이미지 빌드와는 별도 과정입니다. 완성된 패키지가 있으면 동일한 조건의 다음 실행에서 모델 준비를 반복하지 않지만, 서빙에 필요한 가중치와 실행 자원은 다시 불러옵니다.

rank 수를 바꾸면 그 수에 맞는 패키지를 새로 준비해야 합니다. 스크립트가 다른 패키지 디렉터리를 자동으로 선택하므로 이미지를 다시 빌드할 필요가 없으며, 기존 패키지도 유지됩니다. 새 rank 수에 맞춰 모델 로딩, 그래프 캡처와 내보내기를 진행하고, 호환되는 컴파일 캐시는 재사용할 수 있습니다.

## 저장되는 파일과 재사용

모델과 상태 디렉터리는 **이 소스 디렉터리 밖에** 두세요. 상태 디렉터리에는 인증 토큰과 개인 서명키가 저장될 수 있으므로 Git에 올리면 안 됩니다.

| `--state-dir` 아래 경로 | 용도 |
|---|---|
| `preparation/` | 공식 설정, 준비용 토큰과 헤드의 개발용 서명 인증정보 |
| `preparation/export/` | 쓰기 가능한 임시 내보내기 공간 |
| `cache/kernels/` | 커널, 튜닝 및 모델 순전파 컴파일 캐시 |
| `cache/packages/` | 모델 준비 과정에서 재사용하는 패키지 데이터 |
| `packages/<identifier>/` | 헤드의 `model.safetensors`와 함께 필요한 데이터 파일 |
| `public/` | 서명 주체를 확인하기 위한 공개 프로필 |
| `runtime/` | 서빙용 신뢰 정보와 수신한 rank 패키지 캐시 |
| `logs/<launch-id>/` | 각 단계가 끝나거나 실행이 종료될 때 보존하는 컨테이너 로그 |

패키지 디렉터리 식별자는 이미지 ID, 모델 경로와 메타데이터, rank 수, 준비 인자로 결정됩니다. **캐시를 찾기 위한 이름이며 비밀번호나 서명키가 아닙니다.** 현재는 준비 인자의 순서도 식별자에 영향을 주므로 같은 명령을 유지하세요.

내보내기가 끝나지 않았다면 다음 실행에서도 모델 로딩, 캡처와 내보내기를 진행해야 합니다. 기존 튜닝·컴파일 캐시는 재사용할 수 있습니다. 메타데이터를 바꾸지 않고 체크포인트 텐서를 교체했다면 `--fresh`를 사용하세요. 스크립트는 실행할 때마다 모든 가중치의 바이트를 해시 검사하지 않습니다. `--fresh`는 기존 패키지와 캐시를 지우지 않고 별도의 패키지를 준비합니다.

`Ctrl-C`를 누르면 해당 실행이 만든 컨테이너만 종료하고 제거합니다. 상태, 캐시, 패키지와 로그는 SSD에 남습니다. 호스트에 연결하지 않은 컨테이너 내부 경로에만 추가한 파일은 컨테이너 제거 시 사라집니다.

## 공식 동작과 실행 스크립트의 역할

모델 계산, 정밀도 선택, 튜닝, 컴파일, 패키지 형식, 서명, 캐시 관리와 서빙은 FLARE/B12X가 처리합니다. 모델 설정은 실행 인자로 전달하며, Dockerfile에서 동시 요청 수, MTP 깊이, prefill 크기나 메모리 제한을 강제하지 않습니다.

이 프로젝트의 스크립트는 SSH를 통한 실행 관리, 선택적 이미지 전달, 디렉터리 배치, 사전 검사, 재사용할 패키지 선택과 컨테이너·로그 관리를 추가합니다. **이 스크립트는 NVIDIA가 제공한 파일이 아닙니다.** 작은 RoCE 연결 검사를 위한 B12X 네이티브 프록시 등, 고정한 원본 버전의 인터페이스를 사용합니다.

모델 준비 시에는 통신 주소와 일치하는 활성 RoCEv2 IPv4 항목을 찾아, 노드별 B12X HCA/GID 설정을 전달합니다. GID 인덱스를 3으로 고정하지 않습니다. 네이티브 서빙은 FLARE 자체의 통신 장치 탐색을 유지하며, Python B12X용 환경변수로 네이티브 서버의 통신 장치를 고정하지 않습니다.

컨테이너에는 Linux `io_uring`을 사용할 수 있도록 `seccomp=unconfined`를 지정합니다. 이는 컨테이너의 seccomp 필터를 해제하므로 보안상 고려가 필요한 설정입니다. 스크립트는 `--privileged`를 사용하거나 호스트 IP, 라우팅, 방화벽 또는 sysctl을 변경하지 않습니다. 개인 서명키는 헤드에만 남기며 서빙 컨테이너에는 연결하지 않습니다. 패키지 서명을 검증한 뒤, 확인한 로컬 개발키와 이름 공간만 허용합니다.

실행 예시는 API를 호스트의 모든 인터페이스에서 수신하며 API 인증을 설정하지 않습니다. 적절한 신뢰 네트워크에서 사용하고 수신 주소를 의도에 맞게 선택하세요.
